# Анализ требований Kairema v4

**Источник:** пользовательский файл `pasted_content.txt`, строки 1–87.  
**Статус:** анализ требований; код Kairema v3 этим документом не изменяется.

## 1. Что именно меняет v4

Kairema v4 не является косметическим обновлением v3. Спецификация меняет публичную модель продукта с **пяти ролей** на **четыре роли** и заменяет независимый fallback каждой роли на единый механизм здоровья трёх провайдеров: OpenRouter, Google AI Studio и Groq. При этом существующие функции v3 — сохранённые чаты, экспорт с историей, безопасные ключи, личность Kairema, очистка reasoning-блоков, копирование, регенерация и отмена потока — должны остаться без регрессий.

| Область | Требование v4 | Последствие для текущего v3 |
|---|---|---|
| Видимое меню | Ровно 4 роли: Быстрый, Смекалистый, Контекст, Флагман | Публичная карточка «Код» должна исчезнуть; её модели могут остаться только серверными помощниками. |
| Доступность | Все карточки всегда видимы | Нельзя отфильтровывать роли по квоте, health-check или отсутствию результата. |
| Статусы | Готов / Резерв активен / Недоступно / Не настроено | Нужен агрегированный статус роли, а не статус конкретной модели. |
| Маршрутизация | Три провайдера работают как общий пул | Нужен общий `PROVIDER_HEALTH`, учитываемый всеми ролями. |
| Надёжность | После исчерпания квоты один провайдер пропускается всеми ролями | Состояние здоровья должно быть серверным и общим между запросами, а не локальным для одного вызова. |
| Прозрачность | Под ответом — фактическая модель и пометка резерва | Во frontend можно выдавать только модель, провайдера и флаг fallback; скрытые цепи нельзя выдавать. |

## 2. Модель ролей и серверные цепи

Файл задаёт четыре публичных слага: `fast`, `smart`, `context`, `flagship`. Для каждой роли необходим серверный реестр кандидатов с провайдером, фактическим model ID, назначением и приоритетом. В UI должен отображаться только выбранный role slug, человеческое название, агрегированный статус и итоговая модель ответа.

> Рекомендация: `MODEL_ROLES` и `PROVIDER_HEALTH` остаются исключительно в серверном коде. Клиент получает только безопасный DTO роли и метаданные фактически завершённого ответа.

### Обязательная верификация идентификаторов

OpenRouter-slug’и в файле названы фиксированными, но Google и Groq должны быть получены из их живых каталогов `GET /models` непосредственно перед внедрением. В отчёте реализации следует указать только подтверждённые фактические ID и дату проверки. Модели из разделов «Помощники» допустимы как скрытые серверные кандидаты; они не создают новых карточек.

### Критический конфликт: число попыток

В строках 33–34 у «Флагмана» перечислены primary и **четыре** резерва, то есть пять кандидатов. В строке 44 зафиксирован максимум **четыре попытки на запрос**. Эти условия нельзя одновременно выполнить для полной цепи.

| Безопасное правило | Рекомендуемая интерпретация |
|---|---|
| Глобальный лимит | Не более 4 сетевых попыток на один запрос — приоритетнее полного списка. |
| Цепь «Флагмана» | Выполнять primary + первые 3 резерва; `openrouter/free` оставить как диагностический/будущий кандидат, но не вызывать в том же запросе. |
| Видимость | Не сообщать пользователю длину цепи и пропущенные кандидаты. |

## 3. Здоровье провайдера и fallback

Новый механизм требует таблицы или иного общего серверного хранилища `provider_health` с минимумом полей: `provider`, `state`, `blockedUntil`, `lastCheckedAt`, `lastErrorClass` и `updatedAt`. Состояние должно быть атомарно обновляемым, чтобы параллельные запросы не создавали бесконечные повторы.

| Сигнал | Предлагаемая реакция | Влияние на другие роли |
|---|---|---|
| 429 с `retry-after` | Одна контролируемая пауза, затем следующий кандидат | Поставить временный cooldown; не объявлять провайдера исчерпанным навсегда. |
| 429 «budget/quota exhausted» | Пометить провайдер исчерпанным до следующей проверки | Все роли пропускают его кандидатов. |
| 503 или timeout | Короткая задержка, следующий кандидат | Временное ухудшение, повторная проверка позднее. |
| 401/403 | Отключить провайдер до ручного исправления/следующей верификации | Все роли пропускают провайдера. |
| Успешный ответ | Обновить здоровье на готово | Роль может снова использовать провайдера. |

Указанные в файле «при деплое и раз в сутки» пинги являются задачей периодического выполнения. До реализации такой части нужно выбрать поддерживаемый механизм расписаний, обеспечить идемпотентность и не выполнять сетевые пинги с frontend. Сброс статуса «исчерпан» нельзя делать просто по времени: он должен сопровождаться успешной короткой серверной проверкой.

## 4. Поток, отмена и регенерация

Потоковый ответ должен иметь лимит на каждую попытку и прекращать fallback после первого отображённого пользовательскому интерфейсу фрагмента: переключение после частичного текста смешает два разных ответа. Кнопка «Отменить» должна отменять `AbortController` в браузере и серверный upstream; сохранение отменённого черновика должно быть явно определено. Безопасный вариант — не сохранять неполный assistant-ответ как завершённый.

Регенерация должна строиться на последнем пользовательском запросе текущего чата, создавать новое assistant-сообщение и не дублировать исходный запрос. Копирование работает только с текстом ответа, без скрытых технических метаданных.

## 5. Экспорт и приватность

Текущая история экспортов из v3 соответствует направлению v4, но при перестройке необходимо сохранить четыре свойства: файл и метаданные принадлежат пользователю; список отображает только собственные экспорты; скачать и удалить может только владелец; сама история чата не становится доступной по одному только ID экспорта. Содержимое файлов хранится в S3, а в базе — метаданные и владелец.

## 6. Что запрещено и как это влияет на реализацию

Нельзя добавлять Kimi, TTS, embed, rerank, safety или мультимодальные модели в цепи текстового чата. Эти ограничения должны быть отражены не только в UI, но и в server-side allowlist, чтобы запрос не мог обойти правила через подстановку model ID. Любые API-ключи, здоровье провайдеров с техническими подробностями и полный порядок fallback не должны возвращаться в tRPC/SSE payload, логи или bundle.

## 7. Приёмка: что потребуется доказать

| Критерий файла | Проверка |
|---|---|
| Ровно 4 карточки | Desktop- и mobile-скриншоты; программная проверка четырёх role keys. |
| Живой тест ролей | Таблица `Роль / primary / HTTP / model_used / статус` без секретов. |
| Общий failover провайдера | Контролируемый 429 OpenRouter, затем запросы всех ролей выбирают только Google/Groq; UI показывает «(резерв)». |
| Русское качество | Один фиксированный русскоязычный документ с терминологией и переводом, одинаковые параметры и прозрачные критерии сравнения. |
| Безопасность | Поиск по client source и production-bundle: 0 ссылок на секреты и внутренние цепи; проверка отсутствия runtime-ошибок. |
| Регрессия v3 | Тесты сохранённых чатов, экспортов, копирования, регенерации и отмены потока остаются зелёными. |

## 8. Итоговая оценка

Требования v4 технически реализуемы, но это **существенная серверная перестройка**, а не простое изменение карточек. Перед началом разработки требуется принять одно формальное решение: для «Флагмана» при максимуме четырёх попыток использовать только первые три резерва или изменить глобальный лимит попыток. Рекомендуемый вариант — сохранить строгий лимит в четыре попытки, так как он защищает от долгого ожидания и неконтролируемого расхода бесплатных квот.

После такого уточнения реализация должна начинаться с серверных контрактов `MODEL_ROLES` и `PROVIDER_HEALTH`, затем миграции общего состояния здоровья, после чего можно безопасно менять UI с пяти карточек на четыре.
